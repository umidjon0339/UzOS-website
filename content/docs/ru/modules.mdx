# Как устроена UzOS

Ядро разделено на **подсистемы управления** — по папке на каждую внутри `modules/`. Каждая отвечает на один большой вопрос об операционных системах, и все они устроены одинаково.

## Жизнь UzOS в четыре шага

1. **GRUB** загружает `kernel.bin` в память и переходит к `boot/boot.s`.
2. `boot.s` настраивает стек и вызывает `kernel_main` из `modules/core/`.
3. `kernel_main` по очереди запускает все подсистемы (это и есть журнал загрузки).
4. **Оболочка** показывает приглашение входа и ждёт вас.

## 12 подсистем

| Подсистема | На какой вопрос отвечает | Статус |
| --- | --- | --- |
| `process_management` | Что такое процесс? Таблица процессов, переключение контекста, загрузка ELF, системные вызовы, сигналы | Готово |
| `memory_management` | Откуда берётся память? Кадры по 4 КБ, страничная адресация, куча ядра, `sbrk` / `mmap` | Готово |
| `cpu_management` | Кто выполняется следующим? Приоритеты, FIFO / RR, aging, учёт времени CPU, `perf` | Готово |
| `device_management` | Как ядро общается с оборудованием? Таймер, клавиатура, мышь, часы, экран, графика | Готово |
| `io_management` | Что такое файловый дескриптор? `open`, `read`, `write`, `close`, `seek` | Готово |
| `filesystem_management` | Где хранятся файлы? Дерево каталогов, RAM-диск, `/proc` | Готово |
| `user_management` | Кто вы? Учётные записи, пароли SHA-256, вход, владельцы и права файлов | Готово |
| `security_management` | Кто что может и что пытались сделать? Привилегии, журнал аудита, целостность ядра | Готово |
| `shell` | Как работает командная строка? Разбор, история, дополнение по Tab, подсветка | Готово |
| `ui` | Как должен выглядеть вывод? Цвета по смыслу, рамки, индикаторы, строка состояния | Готово |
| `network_management` | Как компьютеры общаются? Драйвер сетевой карты, IP, TCP / UDP, сокеты | В планах |
| `storage_management` | Как файлам пережить перезагрузку? Драйвер диска и файловая система на диске | В планах |

## Одна папка — одна идея

У каждой подсистемы одни и те же четыре папки:

```
modules/cpu_management/
  core/                     то, что вызывает само ядро
    tsc/  tsc.c  tsc.h
  commands/                 по папке на каждую команду
    top/  cmd_top.c  cmd_top.h
  syscalls/                 по папке на каждый системный вызов
    getpid/  sys_getpid.c  sys_getpid.h
  security/                 по папке на каждую атаку
    fork_bomb/
      atk_fork_bomb.c       атака
      README.md             история из реальной жизни
      defence/
        process_quota/
          def_process_quota.c   защита, которая её останавливает
```

| Папка | Что в ней лежит |
| --- | --- |
| `core/` | Только то, что вызывает само ядро (тик таймера, планировщик), или данные, которые должны существовать в одном экземпляре |
| `commands/<имя>/` | Одна команда: `cmd_<имя>.c` и свой заголовок `cmd_<имя>.h` |
| `syscalls/<имя>/` | Один системный вызов: `sys_<имя>.c` и `sys_<имя>.h` |
| `security/<атака>/` | Одна атака (`atk_<атака>.c` + `README.md`), а её защита — внутри `defence/<защита>/` |

## Почему UzOS легко изучать

- **Всё в одном месте.** Всё, что нужно команде, системному вызову, атаке или защите, лежит в её папке. Мелкие вспомогательные функции скопированы, а не вынесены в общие файлы, — чтобы понять одну вещь, не нужно прыгать по проекту.
- **Объяснение рядом с кодом.** Каждый файл начинается с комментария: что он делает, что *использует* и почему написан именно так.
- **Ничего не скрыто.** Каждый `#include` указывает полный путь и что из него берётся:

  ```
  #include "modules/process_management/core/scheduler/scheduler.h"   // scheduler_get_current_process
  ```

- **Сломай, потом почини.** Каждая атака лежит рядом с защитой, которая её останавливает. Запустите её через `seclab`, посмотрите, как её блокируют, и прочитайте оба файла рядом.

Поэтому, чтобы узнать, как работает `top`, откройте `modules/cpu_management/commands/top/`. Весь ответ — в этой папке.

## С чего начать чтение

- **Страничная память**: `modules/memory_management/core/vmm/`, затем попробуйте в оболочке `pagewalk 0xB8000` (текстовая память VGA)
- **Переключение контекста**: `modules/process_management/core/scheduler/switch_task.s`
- **Пароли**: `modules/user_management/core/hash/` — SHA-256, расписанный по шагам
- **Системный вызов от начала до конца**: `modules/process_management/syscalls/handler/`
